# 完成总结：跑批可靠性四修

四项改动都有实跑依据，不是设想。全部 7 个测试脚本通过。

## 一、推送日期（`run_daily.sh`）

`run_daily.sh` 在开头固定 `today` 并传给 `daily_select --date`，但两个推送
脚本没收到，各自去调 `date.today()`。09-03 那轮 16:26 启动、次日 09:12
才走到推送：

```
[push_email] 跳过：CSV 不存在 .../daily_selections_2026-09-04.csv
```

结果在 `..._2026-09-03.csv`。**跑批跨午夜，通知必丢。**

修法是 `export PUSH_DATE="$today"`，脚本本来就支持这个变量，Python 侧未改。

测试覆盖三种情形：当天跑完、跨午夜跑完、以及**复现修复前的错误行为**
（不传 `PUSH_DATE` + 系统已跨日 → 定位到次日 CSV 且找不到文件）。
另确认缺 SMTP/SERVERCHAN 凭据时仍静默退出。

顺带更正我之前的判断：09-01 推送失败我归因于网络，实际是同一个原因。

## 二、耗时护栏（`sync_kline_db`）

09-03 那轮：成功率 95%，每次调用都在 30s 硬超时内返回，但均耗时 18s/票，
跑到 3200 只已过 16.4 小时，整轮 16 小时 46 分。**失败率早停和单次调用
硬超时对这种形态都无效**——一个看失败率，一个看单次调用，没人看总耗时。

新增两道判据，共用既有 `aborted` 路径（因此自动不推进 `last_sync_date`）：

- `max_round_seconds=7200`：整轮墙钟预算 2 小时（正常轮次约 30 分钟，4 倍余量）
- `slow_avg_seconds=3.0` + `slow_min_samples=200`：均耗时超阈值即判定劣化

测试里用可控时钟注入 18s/票，实测输出：

```
too_slow: 已尝试 200 只，单票均耗时 18.0s > 3s，判定上游劣化，
按此速度全市场需 26.0h，剩余 5007 只跳过
```

26 小时这个外推值与 09-03 的实际表现一致。三个护栏置 0 可全部关闭；
正常速度（0.4s/票）不被误杀；失败率早停仍优先生效。

顺手加了 `_fmt_dur`——原先小预算会打成「0.2h 超过 0.2h」，没法判断。

## 三、停牌零值（`_prefilter_cache_has_bad_zero_amount`）

原判据是「近 5 日最高成交额 ≥ 阈值就判缓存有问题」。停牌股停牌前成交额
通常不低，于是必然被误判 → 删整份缓存 → 全市场重扫。09-03 实测 6 只真停牌股
（雪天盐业、有研硅、ST萃华、香山股份、\*ST元道、宇邦新材）就这样让预筛白跑一遍。

判据改为只看**目标日当天**：目标日无行或当日成交额为 0 → 真停牌，放过；
目标日 K 线明明有成交额而缓存记成 0 → 缓存有问题，删。

测试覆盖真停牌（无行 / 当日为 0 / 只有前一日的行）、坏缓存（大额与小额）、
6 只真实停牌股不再误删、停牌股中混入 1 只坏数据仍能识别，
以及零值比例 > 1% 的整体性判据不变。

## 四、成交额精度不被覆盖（改动最大）

`upsert_kline` 原来是 `INSERT OR REPLACE`，没有来源概念。腾讯不返回成交额，
`amount` 由 `均价×volume` 估出；每次 `daily_select` 或生成报告触发按需补拉，
就把精确值改写成近似值。连续三天都得人工修：

| 日期 | 被改写 | P50 | max |
|---|---|---|---|
| 09-01 | 246 | +0.64% | 4.63% |
| 09-02 | 109 | +0.41% | 2.84% |
| 09-03 | 3221 | +0.06% | 3.79% |

而人工修有硬窗口——快照在次日 09:00 左右就翻页（09-04 实测
`日期不符占比 99.75%`，守卫正确拦下），过了就补不回来。

改法：`kline` 表加 `amt_src` 列（幂等迁移，先查 `PRAGMA table_info`），
`upsert` 改 `ON CONFLICT DO UPDATE`，`amount` 与 `amt_src` 按优先级取值——
exact 可覆盖任何值，approx 与未标注都不得覆盖 exact。OHLC/volume/turn/pctChg
不受限制，照常覆盖（近似只发生在 amount 上）。

源标注：sina / baostock / akshare = exact，tencent / mootdx = approx。
mootdx 从未向本库写过一行，其 amount 语义未验证，保守记为 approx。

历史 32.5 万行 `amt_src` 为 NULL，语义是「未知」，按可被覆盖处理——
若当成 exact，历史里那些近似值就再也刷不掉了。

**端到端验证**：把 09-01/02/03 已修正为精确值的 15568 行标为 exact，
然后跑一次 `daily_select` + 一次报告生成，结果：

```
2026-09-01: 可比 5189 行 | amount 被改写 0 行 | amt_src 掉级 0 行
2026-09-02: 可比 5189 行 | amount 被改写 0 行 | amt_src 掉级 0 行
2026-09-03: 可比 5190 行 | amount 被改写 0 行 | amt_src 掉级 0 行
```

改动前同样的操作会改写 100~3000 行。

## 顺带修的一处

`router.py:300` 的 `today_iso` 原来直接用 `pd.Timestamp.now()`，
与 `_is_unsettled` 走的 `_now()` 不是同一个来源，导致「今天」不可测。
改为统一走 `_now()`。这是测试暴露出来的——`require_today` 的基线用例
在换日之后就失败了，因为测试控制不了那个时钟。
