## 关键发现：库里的近似误差比我之前说的严重得多

原值相对 baostock 精确值的偏差分位：

```
P5 = -27.504%   P50 = -0.147%   P95 = +1.169%   |max| = 99.268%
```

中位数只有 -0.15%，这与我之前「腾讯近似误差 P50 -0.157%」的说法一致。
但 **P5 达到 -27.5%**——也就是说有 5% 的行，成交额被低估了四分之一以上。
这个尾部我之前完全没测到，因为过去几次都只对比单日、且只看中位数附近。

尾部的主因是**盘中抓取被固化的半截 K 线**。最典型的是 2026-07-16：

```
2026-07-14  全市场成交额 2.703 万亿
2026-07-15                2.562 万亿
2026-07-16                1.507 万亿   ← 只有邻日 56%
2026-07-17                2.657 万亿
回标后 2026-07-16:         2.397 万亿
```

那一天所有票的 amount 与 volume 偏差**幅度完全相同**（相关性 1.0，
最大偏小 96.8%），说明 amount 是从那个偏小的 volume 估出来的。
`partial-bar-refetch` 那个 spec 修掉了产生机制，但 07-16 在修复之前
就已入库，从未被回补。这次顺带修好了。

早期两个成交额畸低的日期（2025-09-29 五行、2025-10-23 一百四十三行）
不是数据错误，是那时库内覆盖本来就稀疏。我一开始用「与邻日中位数比」
去筛，把它们也标成了异常，那个判据在行数差异大时不成立。

## 顺带排除的一个担心

我担心腾讯的前复权 volume 与 baostock 的不复权 volume 存在系统性差异，
那样回标会让 volume/amount 与 OHLC 口径打架。实测排除了：
大偏差聚集在**单一日期**而非按代码横跨多日，说明两者口径一致。

## 下游验证

跑一次 `daily_select`（09-01/02/03）+ 一次报告生成后：

```
可比 124590 行 | amount 被改写 0 | amt_src 掉级 0 | volume 被改写 1289
```

`amount` 的保护完全生效。但 **volume 会被重新取整**——`amt_src` 机制
按设计只保护 amount，腾讯按需补拉写回的 volume 又变成 100 的整数倍。
影响量级：

```
相对误差 P50=0.00004%  P95=0.00032%  |max|=0.0085%
绝对差   中位数 26 股 / 最大 50 股
```

万分之一以下，对任何量能特征都无实质影响，因此**不打算为它扩展保护机制**——
加一列 `vol_src` 的复杂度换不来对应收益。但这是个已知的、会缓慢回退的点，
记在这里以免日后困惑「明明回标过怎么又是整百」。

## Task 8：`kline.db` 出版本控制的方案（只出方案，未执行）

### 现状

```
.git 总体积                796 MB
kline.db 历史版本数        43
kline.db 累计原始体积      1851.3 MB   ← 占全部 blob 的约 93%
其余大件: tracker_report/index.html 36.5MB
          logs-*.zip 两个共 24.5MB（疑似误提交）
          stock_data/selections.json 11.2MB
当前工作区 kline.db        69 MB
```

每个交易日新增一版 60~70MB，GitHub 每次推送都警告超过 50MB 推荐上限
（100MB 是硬限，按当前增速约 2026 年底触顶）。

### 三条路径

**路径 A：加入 .gitignore，不动历史。**
代价最小，风险最低。停止继续膨胀，但已有的 796MB 不会缩小，
`git clone` 仍要拉全量。需要补一份重建说明（从 baostock/新浪重建
一个 225 日库约 30 分钟，本次回标已经验证了这条路可行）。
**这是我推荐的第一步**——它可逆、不影响任何协作者、随时可做。

**路径 B：转 Git LFS。**
历史仍在，但新版本走 LFS 存储。需要 `git lfs migrate` 才能把历史
搬过去，那本身就是历史重写。GitHub 免费额度 1GB 存储 / 1GB 月流量，
按每天 70MB 的增速两周就超，需要付费。**性价比最差，不推荐。**

**路径 C：重写历史，彻底移除 kline.db。**
用 `git filter-repo --path stock_data/kline.db --invert-paths`，
`.git` 预计从 796MB 降到 60MB 以下。

### 路径 C 的风险与不可逆点

- **所有 commit hash 全部改变。** 43 个提交里引用过的 hash（包括我在
  各 spec 的 doc/summary 里写的那些）全部失效。
- **必须 `git push --force`。** 这是不可逆操作，远端旧历史被覆盖后
  只能靠本地备份找回。
- **GitHub Pages 会重新部署**，期间页面可能短暂不可用。
- 需要先 `git clone --mirror` 做一份完整备份，否则出错无法回退。
- `git filter-repo` 需要单独安装（不在 git 自带工具里）。
- 本仓库只有 main、无协作者、无 open PR，所以强推的连带影响可控——
  这是路径 C 唯一有利的条件。

### 建议

先做路径 A（立即止血，零风险）；路径 C 等到确实被 100MB 硬限逼到墙角、
或者你明确想收拾干净时再做，并且做之前先 `clone --mirror` 备份。
两个 `logs-*.zip` 无论走哪条路都该顺手 gitignore 掉。

**以上仅为方案，本次未执行任何 gitignore 修改或历史重写。**
