# 全历史成交额/成交量精度回标

用户已预先确认「按建议执行，不用问我」，因此本 spec 的两道确认门直接放行，
不再等待逐阶段回复。

## 背景：保护只覆盖了三天

`pipeline-reliability-four-fixes` 给 `kline` 表加了 `amt_src`，
近似值不再覆盖精确值。但存量只标了三天：

```
2026-09-03   5196 行  exact=5190
2026-09-02   5196 行  exact=5189
2026-09-01   5195 行  exact=5189
2026-08-31   5194 行  exact=0
...（共 225 个交易日，最早 2025-09-29，总 341271 行）
exact 总数: 15568 / 341271 = 4.6%
```

也就是说 08-31 及以前的任何一天，成交额仍会被腾讯的 `均价×volume`
近似值改写，而且改了也没人知道。

## 关键发现：一次全量回标只要 14 分钟

原以为要 225 天 × 5207 只 = 117 万次调用。实测 baostock 的
`query_history_k_data_plus` 支持**按代码一次拉整个日期区间**：

```
sh.600000: 225 行 / 0.15s
sz.000001: 225 行 / 0.15s
sh.688169: 225 行 / 0.04s
sz.300750: 225 行 / 0.07s
sh.600519: 225 行 / 0.38s
5 只共 1125 行 / 0.78s -> 单只均 0.16s，5207 只预计 14 分钟
```

**5207 次调用覆盖全部 225 个交易日**，不是 117 万次。

而且返回里 `amount` 与 `volume` 都是精确值：

```
sh.600000 2026-09-03  amount=841972879.6800  volume=89817155
```

所以这一趟不只能修成交额，还能顺手修掉腾讯按「手」上报导致的
volume 取整（腾讯写入的 volume 都是 100 的整数倍，最多差 99 股）。

## 技术方案

新增 `scripts/backfill_amt_src.py`：

```
用法: python3 scripts/backfill_amt_src.py [--start 2025-09-29] [--end 2026-09-03]
                                          [--dry-run] [--limit N]
```

逐只票拉整区间的 `date,amount,volume`，与库内逐行比对后更新：

```sql
UPDATE kline SET amount=?, volume=?, amt_src='exact'
WHERE code=? AND date=?
```

- 只更新库内**已存在**的行，不新增行。回标是修精度，不是补数据；
  补数据有各自的通路（`fill_kline_from_snapshot.py` / `sync_kline_db`）。
- `amount <= 0` 的行跳过（停牌），不把 0 标成 exact。
- baostock 登录失败立即中止（`lg.error_code != '0'`），不写库。
  这个教训来自之前一次：未校验返回值，白跑 750 秒拿 0 行。
- 每 500 只 logout/login 重连一次，沿用 `backfill_prefilter_cache.py` 的做法。
- 分批提交（每 200 只 commit 一次），中断后可重跑，幂等。
- 统计并打印：更新行数、amount 有实质变化的行数与偏差分位、
  volume 有变化的行数、跳过数、失败代码数。

## 影响文件

| 文件 | 改动 |
|---|---|
| `scripts/backfill_amt_src.py` | 新增 |

不改任何选股逻辑，不改取数链路，不改 `upsert_kline`。
只是把库里已有行的 `amount`/`volume` 换成精确值并打上 `exact` 标记。

## 边界与异常

- **这是全库写操作**，执行前必须备份。上一批备份刚清理掉，本次重新建一个。
- 更新后 `amount` 会变，意味着历史特征（量能类）会随之变化，
  历史选股结果理论上可能与当初不同。这是修正而非破坏——当初的
  近似值本就是错的。但需要在 summary 里记录，避免日后复盘时困惑。
- baostock 的 `adjustflag='3'`（不复权）与库内既有口径一致；
  `amount`/`volume` 本身不受复权影响，但仍按既有参数取，避免引入差异。
- 若 baostock 中途不可用，已提交的批次保留，重跑会跳过已是 exact 的行。
- 退市股在 baostock 查不到，计入失败列表，其 `amt_src` 保持 NULL。

## 预期结果

`exact` 覆盖率从 4.6% 提升到接近库内可查行的全部。
此后任何日期的成交额都不会被近似值覆盖，不再需要人工修。
顺带消除腾讯 volume 的取整误差。
