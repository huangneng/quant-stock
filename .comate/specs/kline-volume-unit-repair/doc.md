# kline 成交量单位修复：akshare 的「手」被当成「股」入库

## 问题

`kline` 表 314,426 行里有 **28,995 行（9.2%）**的 `amount` 恰好是
`close × volume` 的约 100 倍。真实关系应是
`amount = VWAP × 股数`，所以 `amount/(close×volume)` 正常应在 1 附近。

比值分布证明这是精确的 100 倍单位错误，不是别的问题：

| `amount/(close×volume)` | 行数 |
|---|---|
| [90, 99) | 4,090 |
| **[99, 101)** | **13,244** |
| [101, 110) | 10,731 |
| [110, 200) | 922 |
| ≥200 | 0 |

围绕 100 的几个百分点离散，正是 `VWAP ≠ close` 造成的，
即 `amount/(close×volume) = 100 × VWAP/close`。

波及 **4,233 只票**，时间跨度 2025-12 ~ 2026-08，
2026-07 最集中（9,891 行）——那正是腾讯不可用、akshare 承担主要取数的月份。

## 根因

`data_hub/sources/akshare.py:38` 直接把东财的 `成交量` 映射成 `volume`：

```python
'最高': 'high', '最低': 'low', '成交量': 'volume',
'成交额': 'amount', '换手率': 'turn', '涨跌幅': 'pctChg',
```

东财 `stock_zh_a_hist` 的 `成交量` 单位是**手**，`成交额` 单位是**元**。
统一 schema 要求 `volume` 是**股**——`tencent_kline.py:51` 明确做了换算：

```python
vol_multiplier = 1.0 if code.startswith(('sh.688', 'sh.689')) else 100.0
```

akshare 缺这一步换算，于是 volume 小了 100 倍，而 amount 是对的。

证据链闭合：这 28,995 行**全部** `turn > 0`，且**没有一行**的 amount 等于
`均价×volume`（腾讯近似式）。`turn` 只由 akshare 和 baostock 填充，
而 baostock 的 volume 本身就是股——所以坏行只可能来自 akshare。

mootdx 也有同样的嫌疑（`mootdx_source.py:81` 把通达信的 `vol` 直接当 `volume`，
通达信的 vol 通常也是手），但它不填 `turn`，所以现存坏行里没有它的份。
需要在上游恢复后实测确认，不能凭推测就改。

## 影响

`volume` 小 100 倍会污染所有量能类特征：量比、放量倍数、换手估算。
`amount` 本身是对的，所以 25 亿预筛不受这个缺陷影响。

## 修复方案

### 源头修复

`akshare.py` 在字段映射后把 `volume` 乘 100。科创板（sh.688/689）需要确认
东财是否同样按手计——腾讯对科创板用的是 1.0 倍率，说明各家口径不一致，
必须实测而非照抄。

### 存量修复

坏行可以确定性识别与修复：`amount` 可信，`volume` 乘 100 即可。
判定条件用 `amount/(close×volume) ∈ [50, 200)`，
上下界留足 VWAP 偏离的余量，且与正常群体（比值 <2）之间有巨大空隙，不会误判。

修复前备份 `kline.db`。修复用一条 UPDATE，不重新取数——重新取数依赖上游，
而上游现在整体不可用。

### 一致性巡检

新增可重复运行的巡检，报告各比值区间的行数，让这类单位错误下次能被立刻发现，
而不是等到人工核对某只票时才偶然撞见。

## 边界与异常

- `close = 0` / `volume = 0` / `amount = 0` 的行无法判定，一律跳过，不做修改。
- 修复是幂等的：修完后比值落回 1 附近，再跑一次不会二次乘 100。
- 停牌票 `volume = 0` 且 `amount = 0`，天然被跳过。
- 科创板倍率未经实测前不动 sh.688/689 的源头逻辑，避免把对的改错。
- 只改 `volume`，不动 `amount`/`turn`——`turn` 是百分比，与成交量单位无关
  （坏行 turn 分布 0.02~85.49，量级正常）。

## 预期结果

比值 ≥50 的行数从 28,995 降到 0，且不产生新的异常区间。
量能类特征在这 4,233 只票的历史上恢复可用。

## 不在本次范围（含对我先前判断的修正）

**中位数只有 -0.2%**，P25~P75 落在 ±0.5% 内。金健米业的 -47% 属于 5.2% 的尾部，
不是普遍情况。而且该尾部的成因是 `volume` 偏小，不是均价近似——
这些票的 `close` 与新浪一致（±1%），偏差全在量上。

所以腾讯的 `amount` 近似**不需要改**。预筛已经用新浪精确快照，
用库内近似值做 25 亿预筛会漏选 12/146 只，这个差距印证了现有设计是对的。

08-28 仍有若干票 `volume` 比新浪少 1.75~9 倍（如 sh.600000 33.6M vs 58.8M），
这与本次的 100 倍单位错误是不同现象，成因未定，需要上游恢复后逐源实测才能定位。
我先前把这个尾部说成「100% 集中在 sh.600」也不准确——那只是 08-28 单日比对的
表象，sh.600519 在同日量能同样偏低却被新浪证实为真实成交。这一项单独排查。
