# K线数据源熔断 — 完成总结

## 结论先说

熔断已实现并通过全部单测与集成测试，但**在 08-24 / 08-25 两天的真实运行中一次都没有触发**。
08-21 的 56101s → 08-24 的 1625s 这个提速**不能归功于熔断**，是上游从"静默慢"恢复到
"快速响应"的结果。熔断的价值目前只在注入测试中得到证明，尚未被真实场景验证。

更重要的是，这轮观测暴露了两个此前未知的问题，其中一个有立即的运维风险（见"新发现的风险"）。

### 熔断设计

每个源一个轮内状态机，`sync_kline_db` 开始时新建、结束时丢弃，不跨轮持久化。
与 R4 的 `failed_codes`（跨轮死码名单）是两个维度：后者记"这只票取不到"，
前者记"这个源现在不通"。

判定口径经过一次实测修正。原设计只把"抛异常"计入连续失败，理由是退市票在所有源上
都返回空、把空数据算失败会误熔断健康源。08-21 证明这个口径不成立：

| 日期 | 失败模式 | `取数异常` 次数 | 熔断 |
|---|---|---|---|
| 08-20 | 腾讯限流抛 `AttributeError` | 每票 1 次 | 设计有效 |
| 08-21 | mootdx 静默超时返回空 | **0 次** | **设计失效** |

08-21 全程 0 次异常却跑了 15.6 小时，因为 mootdx 在库内部吞掉了异常
（`mootdx_source.py:58-63`），只对外返回 `None`，日志里 2388 次
`服务器连接失败`/`Broken pipe` 全是它自己打印的。于是每次调用都判成功、计数反复清零。

修正为 `on_call(elapsed, raised)`：抛异常**或**单次耗时 ≥ `slow_call_s`（默认 3.0s）
判失败。正常成功调用是毫秒级（08-18 全程 575s/5207 只 ≈ 0.11s/只），静默超时是秒级，
而退市票的空返回是快速返回，因此原先的顾虑仍被照顾到。耗时超阈值但拿到了数据时，
数据照常使用，只把该次调用记为失败信号——取数正确性与源健康度是两件独立的事。

## 验证结果

单测与集成测试全部通过：

| 验证项 | 结果 |
|---|---|
| 状态机熔断/试探/恢复 | `fail_threshold=3` 时 3 次失败熔断；`probe_interval=5` 时第 5 次放行；试探成功后归零；试探失败退回熔断并重新计时 |
| 零星失败不误熔断 | 交替失败/成功 50 轮、每 2 次失败被 1 次成功打断 50 轮，`tripped` 恒为 False |
| 降级顺序与登录态 | 腾讯成功则不调后续源；mootdx 登录失败跳过、akshare/baostock 登录失败仍尝试（保持既有语义）；登录态跨调用缓存 |
| 抛异常场景熔断 | 300 只票，腾讯调用 300 → **21** 次（20 探测 + 1 试探），取数成功率仍 300/300 |
| 静默慢调用熔断（08-21 回归） | 连续 20 次慢调用不抛异常，正确熔断 |
| 快速空返回不误熔断 | 退市票模拟 100 次，`slow_calls=0`，未熔断 |
| 与 R4 不冲突 | 全源无数据时 `mark_failed` 照常写入 |
| `breakers=None` 等价性 | 按需补拉路径行为不变 |
| CLI 输出 | 无熔断时零新增噪音；熔断时输出 `breaker_tripped=mootdx(skipped=4900,probes=25,slow=45)` |
| 端到端回归 | `daily_select.py --date 2026-08-20` 候选仍 2 只，评分与重构前一致（0.5442 / 0.2988） |

## 真实观测（Task 6）

| 日期 | synced | failed | 耗时 | 熔断 | 覆盖 |
|---|---|---|---|---|---|
| 08-18 | 5191 | 16 | 575s | —（改造前） | 5196 |
| 08-19 | 5195 | 12 | 1710s | —（改造前） | 5192 |
| 08-17 | 4436 | 586 | 4006s | —（改造前） | 5196 |
| 08-20 | 4742 | 103 | 16367s | —（改造前） | 5181 |
| 08-21 | 3888 | 1319 | **56101s** | 未触发（口径缺陷） | 4809 |
| 08-24 | 2482 | 2416 | 1625s | **未触发** | 2790 |
| 08-25 | **0** | 5207 | 1533s | **未触发** | 无数据 |

两天都没触发的原因各不相同：

- **08-24**：上游已恢复，调用是快速的，没有可省的等待——不触发是正确行为。
- **08-25**：上游全挂但是**快速失败**（1533s / 5207 只 ≈ 0.29s/只）。熔断在这种场景下
  本来也没有收益：没有等待时间可省。

结论：熔断只覆盖"慢"，覆盖不了"全挂"。全挂场景需要的不是跳过某个源，而是尽早识别
并放弃整轮 + 告警，这属于本次范围外。

## 附带修复：预筛空表崩溃

08-25 的 `daily_select` 直接崩了：

```
daily_select.py:211 KeyError: 'amount'
[2026-08-25 16:44:44] !!! daily_select.py failed rc=1 (skip push)
```

链条是：实时快照返回空 → 回退 baostock 逐只查询 → 5207 只全部查不到 → `rows` 为空
→ `pd.DataFrame([])` 是无列空表 → 取 `cache_df['amount']` 抛 `KeyError`。

后果比"0 只候选"严重得多：`run_daily.sh` 判 `rc=1` 后跳过推送，邮件和 ServerChan
都没发，只能靠事后翻日志才发现这天丢了数据。

已在 `cache_df = pd.DataFrame(rows)` 之后加空表守卫，返回 `[]` 让流程正常产出
0 只候选并触发推送。验证：上游全挂返回 `[]` 不再抛异常，缓存命中的正常路径不受影响。

遗留：守卫让流程不崩，但无法区分"今天真的没有符合条件的票"与"今天数据源挂了"，
两者都是一封"0 只候选"的邮件。要区分需要把告警信息带进推送标题，需改
`daily_select` 与两个推送脚本的接口，未做。

## 新发现的风险（需尽快处理）

`failed_codes` 已积累到 **5207 行——全市场每一只票都在里面**，`retry_cnt` 分布：

| retry_cnt | 只数 |
|---|---|
| 1 | 2690 |
| 2 | 2118 |
| 3 | 374 |
| 4 | **25** |

R4.2 的死码跳过阈值是 `skip_retry_gte=5`，设计意图是跳过退市/长期停牌的标的。
但连续几天的上游中断会把**全市场**的 `retry_cnt` 一起推过阈值。目前最大值已到 4，
**再来一个全挂的交易日就会有票达到 5**，此后增量同步会在 7 天窗口内跳过它们，
而且随着更多票达标，跳过范围会持续扩大——最坏情况是整个市场被自己的黑名单锁死，
且因为被跳过就不会再有成功记录去 `clear_failed`，形成自锁。

这是 R4.2 的设计缺陷：它假设"连续失败"意味着标的本身有问题，没有区分
"标的死了"与"上游挂了"。可行的修正方向是在 `sync_kline_db` 里加一道全局判断——
当本轮整体成功率极低（说明是上游问题而非个股问题）时不写 `mark_failed`，
或者把 `mark_failed` 的触发条件收紧为"该轮整体健康但这只票失败"。

**建议在下一个交易日之前处理，否则可能出现整轮同步跳过全市场。**

## 范围外（本次不做）

- **不引入并发**。四源共享可变状态：腾讯共用 `requests.Session`（`tencent_kline.py:40`）、
  mootdx 共用 TCP `Quotes` 客户端（`mootdx_source.py:46`）、baostock 是模块级全局登录态
  且每 500 次调用重连（`baostock.py:43-49`）、akshare 走全局模块。直接套
  `ThreadPoolExecutor` 会出连接池竞争与 TCP 协议错乱；需给每线程各建一套源实例。
  仓库现无任何 `ThreadPoolExecutor`/`asyncio` 用法。另外从 08-25 看，"全挂"场景下
  并发也救不了——没有数据可取。
- 不改各源 timeout 与内部重试。
- 不做跨轮的源健康度持久化。
- 不调整源优先级顺序。
- 不碰选股策略、评分权重。
- 未做"整轮早停 + 告警"与 `failed_codes` 的自锁修正，均记录于上。
