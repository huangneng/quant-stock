# 完成总结：接入东方财富 push2his 直连日K源 —— 验证阶段否决

## 结论

**本方案在 Task 1 验证阶段被否决，未进入编码。** 无半成品代码遗留
（`eastmoney_kline.py` 未创建，`router.py` 未改动）。

## 否决依据（实测）

东财 push2his 端点在**约 12 次请求后即封禁本机 IP**：

```
push2his.eastmoney.com  TCP 443  ->  不通
API 请求                ->  RemoteDisconnected，停 20s 未恢复
同一时刻对照：腾讯 HTTP 200 / 新浪 HTTP 200  （证实是东财单方面封 IP，非本机断网）
```

调研资料称东财限流约 "500 次/日"，实测远比这激进，十几次即触发 IP 级封锁。

## 为何这一条就足以否决

本源的设计定位是放在降级链**链首**、承担**全市场 5207 次/天**的逐票取数。
一个"十几次就封"的源用在这个位置，后果是：

- 同步开始一分钟内即被封，之后每只票都要空等它超时/失败再降级到腾讯；
- 不但拿不到"精确成交额 + 前复权"的预期收益，反而给每只票平白加一道
  无用的失败等待，比现状更差。

昨天单次调用能返回精确数据，是"未触发限流时的样子"，不可持续。
最初基于单次成功就把它推荐为主力，判断下得过早——Task 1 的验证正是为
拦截这种情况而设，此次达到了目的。

## 与现有源的关系

放弃本源后维持现状：**腾讯逐票同步 + baostock 事后回标**。这套虽是两步，
但 09-11~09-17 一周的实践已证明能把数据补至 100% 完整 + 精确成交额，可用。

## 复用的经验

- 东财系（push2his / akshare 底层 / efinance）与腾讯 WAF 属同一类激进反爬，
  不适合承担高频全市场取数。后续若再找免费替代，方向应是"能承受高频逐票"
  的源，而非东财系。
- 通达信直连（pytdx/mootdx）本是免费无 token 的理论最优（不走网页、不被封 IP、
  精确成交额），但本机 7709 端口不通，此环境同样不可用（见 `datasets`/调研记录）。
- 免费无 token 生态里不存在"按日期批量"的 K 线接口；当日批量只有快照
  （新浪，已在用）。历史逐票的慢与被封是免费方案的固有约束，只能靠
  节流/熔断/耗时护栏 + 事后回标来吸收，无法靠换源根治。
