# 盘中半截 K 线被永久固化：重构最近窗口的同步跳过规则

## 问题

08-28 全市场与新浪精确值比对（5192 只可比对）：

| volume 偏差 | 只数 | 占比 |
|---|---|---|
| 一致 | 4,890 | 94.2% |
| 库偏小 <1.5x | 50 | 1.0% |
| 库偏小 1.5~3x | 225 | 4.3% |
| 库偏小 3~20x | 27 | 0.5% |

302 只（5.8%）成交量偏小 1.01~9.07 倍，**全部是 sh.600xxx**（该板块 747 只，占 40%）。
价格字段是对的（close 比值 P50=1.000、P99=1.009），错的只有量。
302 只里 297 只 `turn=0`，即腾讯源写入。

**17 只是历史选股标的**，包括刚提交的 08-28 候选 `sh.600127` 金健米业：
库内量 156,523,700 vs 实际 289,228,230，偏小 1.85 倍。

## 根因（已实测确认）

腾讯接口现在返回 `sh600133` 的 08-28 成交量是 `379,084` 手 ×100 = **37,908,400 股**，
与新浪 37,908,372 一致（比值 1.000），价格也一致。
而库里存的是 `4,181,400` 股 = `41,814` 手——**是当日成交量的 11%**。

所以库里那一行是**盘中某个时刻的半截 K 线**，不是收盘完整数据。

固化机制在 `data_hub/router.py` 的 `sync_kline_db`：

```python
last = self.db.get_last_date(code)
if last and last >= end:
    continue
```

一旦盘中写入了 `date = 08-28` 的半截行，收盘后再同步时 `last >= end` 成立，
该票被直接跳过，半截行永远得不到覆盖。

两个条件凑齐才会出问题，而 08-27 / 08-28 正好都凑齐了：
盘中跑过同步轮次（那两天各有 2~3 轮重试风暴），且收盘后的轮次会跳过它们。
sh.600 集中也印证这一点——universe 是从 `sh.600000` 开始遍历的，
盘中那几轮只跑到前 500~750 只就中断了。

## 技术方案

### 修复一：跳过规则改为「只跳过严格更新的」

```python
# 半截 K 线问题：盘中写入的 date==end 行只含到当时为止的成交量，
# 收盘后如果因为 last >= end 而跳过，这一行就被永久固化。
# 改为只在库里已有超过 end 的数据时才跳过。
if last and last > end:
    continue
```

代价：同一天重复跑时不再有「已是最新、直接跳过」的加速，每轮都会完整重取
5207 只。按 0.3s 节流约 26 分钟——这是正确性的必要成本，
而且盘后本来每只都要取当日数据，跳过逻辑真正省下的只有重跑场景。

### 修复二：盘中不写当日 K 线

`_fetch_kline_online` 之外，`get_kline`（按需补拉路径，`router.py:240`）
也会 `upsert_kline`。选股与报告生成都走这条路，如果在盘中被调用，
同样会写半截行。

在 `sync_kline_db` 与 `get_kline` 的落库前统一加一道守卫：
当 `date == 今天` 且当前时间早于收盘（15:00）时，**不落库该行**，
但仍可返回给调用方使用。盘中拿到的实时数据对选股有意义，
写进历史库则是污染。

### 修复三：存量修复——强制重取最近窗口

不做「检测哪些行是半截」——检测需要逐只比对参照源，而参照只有当日快照。
直接对 08-21 ~ 08-28 窗口内所有票强制重取并覆盖：腾讯当前可用，
返回的是完整收盘数据（已实测比值 1.000）。

复用 `sync_kline_db(start, end, full=True)`：`full=True` 会绕过
`get_last_date` 的跳过逻辑，逐只重取整个区间并 `upsert` 覆盖。

### 修复四：巡检增加半截行检测

`scripts/audit_kline_integrity.py` 增加一项：拉当日新浪快照，
比对最后一个交易日的 `volume`，报告偏差超 1% 的票数。
这是唯一能发现半截行的手段——单靠库内自洽性检查发现不了，
因为 `amount` 是用同一个偏小的 volume 算出来的，比值仍然是 1。

## 边界与异常

- 落库守卫只拦「当日且未收盘」，回补历史日期不受影响。
- 判定收盘用 15:00；集合竞价收盘为 15:00，快照时间戳实测为 15:34 左右，
  取 15:00 作为分界是保守的（15:00~15:34 之间写入的行仍可能不完整，
  由修复一的重取兜住）。
- 非交易日调用时 `date == 今天` 不成立（当日无 K 线），守卫不会误拦。
- `full=True` 重取会覆盖窗口内所有行，包括正确的行——幂等，不产生副作用。
- 修复三执行前备份库；腾讯若中途被 WAF 封，熔断会在 20 只内跳闸并早停，
  此时窗口只修了一部分，需在上游恢复后重跑（重跑幂等）。

## 数据流

```
盘中调用 get_kline(code, start, today)
  └─ 在线取到含今日的半截行
       ├─ 旧行为：upsert 落库 → 收盘后 sync 因 last>=end 跳过 → 永久固化
       └─ 新行为：守卫拦住不落库，仅返回给调用方
                  收盘后 sync 正常取完整行落库

盘后 sync_kline_db(start, end)
  └─ last > end ? 跳过 : 重取并覆盖   ← 由 last >= end 改为 last > end
```

## 预期结果

08-21 ~ 08-28 窗口内所有票的 `volume` 与新浪一致（偏差 >1% 的票数为 0）。
金健米业 08-28 的量从 156,523,700 修正到 289,228,230，
其 `amount` 也随之从 17.39 亿修正到约 32.9 亿——与新浪精确值 32.92 亿吻合。
此后盘中运行选股或生成报告不再污染历史库。
