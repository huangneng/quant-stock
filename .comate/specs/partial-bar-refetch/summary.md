# 半截 K 线修复 — 实施总结

## 结论

盘中写入的半截 K 线被同步跳过规则永久固化。08-28 有 302 只票、08-27 有 437 只票
的数据是错的。**不止成交量错，价格字段也错**——这一点比立项时判断的严重。

修复后 08-28 全市场 5,192 只成交量与新浪参照 100% 一致（偏差 >1% 的票数为 0）。
08-28 的选股结果因此发生实质变化：金健米业信号由 `gap` 变为 `breakthrough`，
3 星 → 4 星，score 0.5328 → 0.6127。

## 根因

`sync_kline_db` 原本的跳过规则：

```python
if last and last >= end:
    continue
```

盘中一旦写入 `date == end` 的半截行，收盘后同步时 `last >= end` 成立，
该票被跳过，半截行永远得不到覆盖。08-27 / 08-28 两天各跑过 2~3 轮盘中重试，
正好凑齐「盘中写入 + 盘后跳过」这两个条件。

实测坐实：腾讯返回 `sh600133` 的 08-28 成交量是 379,084 手 ×100 = 37,908,400 股，
与新浪 37,908,372 一致；而库里存的是 4,181,400 股，**是当日成交量的 11%**。

## 对立项判断的修正

**立项时我写「价格字段是对的（close 比值 P50=1.000、P99=1.009）」，这个说法有误导性。**
那是全市场中位数；受影响子集的 close 偏差最大到 3.3%，而且**08-27 的价格错得更多**：

全市场逐日改动统计（修复前后对比）：

| 日期 | 价格字段变化 | 成交量变化 | 总数 |
|---|---|---|---|
| 2026-08-21 | 1 | 18 | 5,193 |
| 2026-08-24 | 1 | 15 | 5,192 |
| 2026-08-25 | 0 | 16 | 5,192 |
| 2026-08-26 | 0 | 15 | 5,193 |
| **2026-08-27** | **426** | **437** | 5,193 |
| **2026-08-28** | **282** | **302** | 5,192 |

半截 K 线里除了 `open`，`high` / `low` / `close` / `volume` / `amount` 全都是
截取时刻的值，不是收盘值。以 `sh.600127` 为例：

| 日期 | 字段 | 修复前 | 修复后 |
|---|---|---|---|
| 08-27 | close | 9.99 | **10.78**（当日涨停） |
| 08-27 | high | 10.41 | 10.78 |
| 08-27 | volume | 28,251,900 | 130,434,300 |
| 08-27 | pctChg | 1.94% | **10.00%** |
| 08-28 | close | 11.40 | 11.77 |
| 08-28 | volume | 156,523,700 | 289,228,200 |
| 08-28 | pctChg | 5.75% | **9.18%** |

关键在于**小的 close 误差会放大成大的 pctChg 误差**：08-28 的 close 只差 3.1%，
但 pctChg 从 5.75% 变成 9.18%——因为 pctChg 是「差之差」，
两天的 close 都错时误差叠加。而信号判定用的是 pctChg 阈值，所以会直接翻转分类。

## 单测结果（全通过）

- `last == end` 时该票仍被重取，且起点取 `end` 本身
- `last > end` 时仍然跳过；`last < end` 时起点仍为 `last + 1`
- 14:00 判定当日为未定型、历史日为已定型；16:00 判定当日为已定型
- 盘中 sync：`upsert` 次数 0、`skipped_unsettled = 1`
- 盘后 sync：正常落库
- 盘中回补历史日期不被误拦
- 盘中同时取到 08-27 + 08-28 时，只落库 08-27
- `_drop_unsettled` 对 None / 空表 / 无待拦行的处理正常
- 既有六套单测（WAF、熔断恢复、空返回、节流、早停、akshare 单位）复跑全部通过

实现上把时间源抽成了 `_now()`。第一版测试直接 patch `pd.Timestamp`，
撞上 `sync_kline_db` 内部另一处 `pd.Timestamp(end)` 造成递归爆栈——
抽一个函数比在测试里做全局替换干净。

修复前基线（`--check-latest`）：偏差 >1% 共 302 只（偏小 1~50% 有 176，
50~90% 有 126），其中 17 只是历史选股标的。

## 新发现的严重缺陷（未处理，待决定）

**mootdx 没有设读超时，会让整条流水线无限期挂死。**

存量修复的那个进程从 08-29 22:02 卡到 08-31 09:26，**37 小时累计 CPU 时间
只有 8.38 秒**，完全阻塞在 I/O；WAL 文件 35 小时没有任何写入。
`lsof` 显示它持有一条 `->114.94.20.92:10030 (CLOSED)` 的连接——
通达信端口，连接已关闭而进程仍卡在读上。

这比之前处理过的「慢」严重一个量级：**熔断器对此完全无效**，
它只评估已完成的调用，一个永不返回的调用连 `on_call` 都进不去。
今天 16:15 的 launchd 跑批若撞上同样情况，`sync_today` 会挂死，
`daily_select` 永不执行，也就没有推送。
