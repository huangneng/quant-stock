# 完成总结：快照优先的补数通路 + 预筛兜底不再空转

## 一、快照源不再谎报日期

`data_hub/sources/sina.py` 原来把 `date` 填成 `pd.Timestamp.now()`，
新浪响应第 30/31 位自带的行情日期与时间从未被解析。现在解析出来，
日期缺失即丢弃该行。实测（09-02 08:31 开盘前）：

```
sh.600000 浦发银行 date=2026-09-01 time=15:34:59
sz.000004 国华退   date=2026-07-13 time=16:34:30
```

改动前这三行都会返回 `date=2026-09-02`。

连带修掉 `router.py` 的 `require_today` 分支：原来无条件把快照行拼进
K 线，`date` 原样带入且只判断 `today_iso not in df['date']`。基线测试
暴露两个既有缺陷——开盘前调用会把前一日收盘伪装成今日行，且会与库内
同日行产生重复（实测同一日期两条）。现在只在 `row['date'] == today_iso`
时拼接，并按 date 去重。

`SinaSource.get_kline` 是第三个消费方，不在取数降级链里，改动后语义变正确。

## 二、新增 `scripts/fill_kline_from_snapshot.py`

把手工用了三次的补数流程固化。守卫：日期不符占比 > 1% 中止、
覆盖率 < 95% 中止、停牌行跳过、`pctChg` 用快照昨收算、`--dry-run`。

实测 09-01：快照返回 5193 只，可写 5189 行，覆盖率 99.7%，**2.0 秒**。
日期不符恒定 4 只，全是退市股（国华退/恒久退/赛隆退/天龙退）。

耗时对比（同一批数据）：

| 通路 | 请求数 | 耗时 | 结果 |
|---|---|---|---|
| 腾讯日K 逐票 | 5207 | 34 分钟 | 553 只（WAF 拦截） |
| baostock 兜底 | 5207×3 | 4.5 小时 | 0 行 |
| 新浪快照 | 9 | **2 秒** | 5189 行，精确 |

## 三、预筛不再空转

- 快照失败重试 3 次、退避 2/4 秒（成本仅 9 个请求）。
- 放开历史日期：不再要求 `end_date == today`，快照自带日期等于目标日即可用。
  这正是 09-01 能在次日开盘前补出来的机制。
- 快照里日期不符的行被剔除，不混进缓存。
- baostock 兜底加早停（样本 200 / 失败率 0.9），语义与 `sync_kline_db` 一致。
  测试实测：全失败时调用 600 次即退出，而非跑满 3000 次。
- 空结果不再落盘。清理了 `cache/` 里 **16 个** 1 字节空缓存
  （doc 里我写的"两个"低估了，实际 16 个）。

## 四、两个过程中查出来的问题

### 4.1 候选数从 14 变 3，原因不是我的改动，是我删掉了一个掩盖 bug 的空文件

`daily_select.py:431-440` 读新高榜安全网用的成交额，`_final` 优先、
普通缓存兜底。但 `break` 无条件执行——`_final` 只要**存在**就跳出，
哪怕它是个 1 字节坏文件、`read_csv` 抛异常被 `except: pass` 吞掉、
`_amount_map` 留空。

后果：`if amt is not None and amt < min_amount: continue` 这条
"成交额不足不补入"形同废止，新高榜 47 只被无条件全量放行。

09-01 上午那次跑出 14 只候选，就是踩了这个：其中 11 只成交额低于
25 亿门槛，最小的 \*ST大晟只有 **0.39 亿**。我在 Task 8.4 删掉那 16 个
空缓存后，普通缓存生效、成交额可知，结果回到 **3 只**。

**3 只是符合既有规则的正确结果，14 只是 bug 产物。** 已把 `break`
改为仅在真的读出成交额时执行，这样将来再出现坏缓存也不会静默放行。
选股策略本身（cond1/cond2、25 亿阈值、评分权重）一行未改。

### 4.2 跑 daily_select 会把精确成交额退化成腾讯近似值

补完 09-01 再跑一次 `daily_select`，库内有 **170 只** 的 `amount` 变了，
相对偏差 P50 0.67%、最大 3.78%。这 170 只 = 预筛入池 127 只
**全部** + 安全网补入 43 只，一个不多一个不少。

机制：`Router.get_kline` 第 3 步在按需补拉后会 `upsert_kline`，
而它走的是取数降级链（腾讯优先）。腾讯不返回成交额，`amount` 是
`均价×volume` 估的。**upsert 没有源优先级概念，精确行会被近似行覆盖。**

这次已用补数脚本把 09-01 恢复成精确值（与预筛缓存一致率 100%）。
但这是个未修的缺陷：**目前必须"先跑选股、后跑补数"，顺序反了就退化。**
建议后续开 spec 给 `upsert_kline` 加源优先级或精度标记。不在本次范围内。
