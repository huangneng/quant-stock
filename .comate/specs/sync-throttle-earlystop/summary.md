# 同步节流与整轮早停 — 实施总结

## 结论先说

节流与早停本身都实现正确、单测全过，但**真实跑批证明这两项不足以解决问题**。
2026-08-28 18:34 起跑的一轮同步耗时 **44752s（12.4 小时）**，对比健康日基线 575s
是 **78 倍**。早停没有触发，因为整轮失败率只有 5.2%——降级链最终把数据取到了，
只是慢得离谱。

**因此没有恢复 launchd 任务**（Task 6.4 的前置条件"确认无误早停"未满足）。
两个任务当前仍是 unloaded 状态。

## 改动清单

| 文件 | 改动 |
|---|---|
| `data_hub/sources/tencent_kline.py` | `get_kline` 在 `json.loads` 前检查 HTTP 501 / 响应体含 `waf.tencent.com`，命中则告警并返回 `None` |
| `data_hub/router.py` | 新增 `_Throttle`；`Router.__init__(min_request_interval_s=0.1)` + `_throttle_for`；`_fetch_kline_online` 在发请求前 `wait()`；`sync_kline_db` 新增 `early_stop_min_samples=300` / `early_stop_fail_rate=0.9`，返回值加 `aborted`，早停时不写 `last_sync_date` |
| `data_hub/api.py` | 透传两个早停参数，docstring 补 `aborted` |
| `data_hub/__main__.py` | `aborted` 非空时打印中止原因与"last_sync_date 未推进"提示 |

## 单测结果（全通过）

- WAF 识别：501 → `None` + 告警；200 但响应体含 waf 域名 → 同样识别；正常响应解析不受影响；空响应不误判
- 节流：`min_interval=0.05` × 10 次 = 0.470s；`min_interval=0` = 0.0000s（可关闭）；两源独立计时（同源二次 0.203s / 新源首次 0.0000s）
- 熔断跳过的源零节流成本：`min_interval=0.5` 下 20 次调用 0.0001s，对照未熔断 9.56s
- 早停：全失败 500 只在第 300 只中止（源调用 300 次）；失败率 50% 跑满 500；仅 200 只样本不足不早停；`min_samples=0` 可关闭
- `skipped_dead` 不稀释失败率：300 死码 + 100 全失败 → `attempted=100`
- 早停时 `last_sync_date` 未写、`marked_failed=0`；正常跑完 `last_sync_date=2026-08-28`
- 回归：熔断统计与 `breakers=None` 路径行为不变；CLI 正常跑完无新增输出行

## 为什么早停没救回来（根因）

`_SourceBreaker.on_call(elapsed, raised)` 只把「抛异常」和「耗时 ≥ 3s」判为失败。
WAF 拦截返回 501 的耗时是 **0.07s**，既不抛异常也不慢，于是走 `on_success()`。
后果是三重的：

1. 腾讯 100% 被封，熔断器却一次没跳，5207 只票全部照常请求被封的端点
2. 持续打 WAF 端点让封禁自我延续——本轮开始前刚探到 200，跑到第 1600 只左右
   就重新被封，跑完后再探仍是 501（0.07s）
3. 腾讯每只都空手而归 → 全部下沉到 mootdx / akshare / baostock，
   12 小时就是在这条降级链上耗掉的

baostock 熔断只在第 8.9 小时跳了一次，同源另一个问题：`on_success` 单次快速调用
就把 `tripped` 和 `consecutive_fails` 全清零，而 baostock 是「慢失败夹杂快速空返回」，
连续计数永远攒不到 20。

## 遗留问题（未在本 spec 范围内）

1. **`on_call` 应把「快速空返回」也计为失败信号**——这是本轮 12 小时的直接原因，
   优先级最高。需要把 `get_kline` 的返回是否为空传进熔断判定。
2. **`on_success` 应要求连续 N 次成功才解除熔断**，避免间歇性可用的源反复重置。
3. 腾讯 IP 仍处封禁中（2026-08-29 07:xx 探测 501）。0.1s 节流不足以避开 WAF，
   需要更保守的间隔或改走快照通道（5207 请求/天 → 9 请求/天）。
4. launchd 两个任务保持 unloaded，恢复前应先解决第 1 项。
